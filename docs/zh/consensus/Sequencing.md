# 排序与结算（Rollup 侧）

Rollup 把执行搬下链之后，「谁决定交易顺序」和「状态何时算最终」换了一套机制：**排序器（sequencer）**先给出软确认，欺诈证明（optimistic）或有效性证明（ZK）再把它落成 L1 意义上的最终状态。这不改变 L1 共识，但它引入了一类新的信任问题——排序权集中。

## 四要素

- **在哪一层**：[计算层](/zh/layers/Compute)入口 + [结算层](/zh/layers/Settlement)回锚——排序在执行之前，结算最终回到 L1 的共识
- **解决什么**：Rollup 交易的排序与最终性——把「每秒数千笔的排序」放在链下做廉价完成，再用密码学或博弈手段保证「错的序列最终不会被 L1 接受」
- **解决得怎么样**：生态事实标准是**单排序器**（Arbitrum、Optimism、Base 都是），延迟低、体验接近 Web2，但排序器成了多次事故源：Arbitrum 排序器 2023-02-25 故障停写约 10 小时，Optimism（2023-06）与 Base（2023-09）各有小时级/分钟级停机——停机期间用户只能等，抗审查靠 L1 强制纳入通道兜底；共享排序（Espresso 等）与 based 排序想解决集中化，2025 年为止还没有大规模生产部署
- **出处**：Optimism 排序器文档（<https://community.optimism.io/docs/how-sequencers-work/>）；Espresso Systems（<https://espressosys.com/>）

## 核心机制

- **排序器软确认**：交易进排序器立刻回执（~200ms 体验），批量压缩后 posting 到 L1 数据可用层；顺序由排序器单独决定——这就是它的全部权力。
- **强制纳入（forced inclusion）**：用户可以经 L1 交易把交易塞进 Rollup 的收件箱（Arbitrum 延迟收件箱约 24 小时、OP 数小时内），排序器必须处理——审查收益有限，代价是慢。
- **乐观结算**：状态根默认可信，挑战窗口内（OP Stack 约 7 天）任何人可用**欺诈证明**证伪错误状态根——信任 + 惩罚。
- **ZK 结算**：每批状态转移附**有效性证明**，L1 合约验证通过即最终——密码学保证，无挑战窗口，但证明生成成本高。
- **排序去中心化三路线**：共享排序（多条 Rollup 共用一套去中心化排序节点，跨链原子性附带解决）、based 排序（排序权交给 L1 提议者，继承 L1 的去中心化）、排序器联盟/轮换（Rollup 自己选委员会）。

## 与同族协议的差异

| 方案 | 排序者 | 最终性 | 现状 |
| --- | --- | --- | --- |
| 单排序器（Arbitrum、OP、Base） | 项目方运营的单点 | 乐观 7 天 / ZK 数小时 | 事实标准 |
| based 排序 | L1 提议者 | 同上 | OP 路线图方向，未主流部署 |
| 共享排序（Espresso、Astria） | 专用去中心化网络 | 同上 + 跨 Rollup 原子性 | 早期 |
| L1 直接排序（无 Rollup） | 全体验证人 | L1 共识直接给 | 吞吐上不去 |

## 失败模式

- **排序器停机**：L2 整体不可写，只能读与退出——Arbitrum 10 小时停机是教科书案例；资金安全无损，可用性完全依赖运营方。
- **排序权 MEV**：单排序器 = 单点抢跑/夹击权，且比公链 MEV 更无制衡。
- **挑战机制失效**：optimistic 路线的欺诈证明若因 bug 或升级错误在窗口内无法提交，错误状态根即成最终——历史上各 Rollup 的欺诈证明都经历过「长期无人能成功提交」的阶段。
- **升级密钥**：排序器与合约升级权限集中在运营方——「可维护面」就是攻击面（见[智能合约漏洞](/zh/hacking/SmartContractVulnerabilities)）。

Rollup 排序的本质：**把 L1 共识贵的那部分（全球验证）留给结算，把便宜的那部分（排队）交给一个可问责的角色**——争议全部集中在「这个角色要不要去中心化」上。
